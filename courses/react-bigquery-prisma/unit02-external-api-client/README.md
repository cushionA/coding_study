# unit02: 外部APIクライアントを作る

このユニットを終えると、外部APIから取ってきた生のJSONを「信用しないで」
検証し、アプリ内のきれいな形に変換し、失敗しても賢く(場合によっては)
再試行できるAPIクライアントを一人で書けるようになる。これは「外部データを
DBに保存する」というこのコースのゴールの入口そのものになる。

## なぜ学ぶか

実務で外部APIを叩くコードを書くと、まず「素朴にfetchしてasで型を付ける」
という書き方をしがちだが、これは幻想の安全性でしかない。TypeScriptの型は
コンパイル時にしか存在せず、実行時にAPIが約束を破ったJSON(フィールドが
抜けている、型が違う)を返してきても、コンパイラは何もしてくれない。
本番で初めて`undefined.trim()`のようなエラーが起きて気づく、という事故が
実際に多発する。このユニットではまず「実行時に検証する」習慣を叩き込み、
そのうえで外部APIの一時的な障害(レート制限やサーバエラー)を賢くリトライ
する、実務で通用するAPIクライアントの型を作る。

## 概念: TypeScriptとC#の対応

- **実行時検証(zod)**: C#の`DataAnnotations` + `Validator.TryValidateObject`
  に近いが、決定的に違うのは**型がスキーマから自動で生える**(`z.infer`)点。
  スキーマを1回書けば、それに対応するTypeScriptの型を別に書く必要がない。
- **DTOとドメインモデルの分離**: 外部APIが返す形(`book_id`のような
  snake_case、境界の外側)と、アプリ内で使う形(`id`のようなcamelCase、
  境界の内側)を分ける。C#で言えば、外部サービスのレスポンスDTOクラスと
  自社ドメインのエンティティクラスを分けてマッピングするのと同じ発想。
- **失敗の分類とリトライ**: 404(こちらのミス)は何度再試行しても直らない
  が、429(レート制限)や5xx(相手の一時的な障害)は少し待てば直る
  ことがある。この切り分けをせずに全部リトライすると、直らないエラーで
  無駄にリトライし続けることになる。
- **指数バックオフ+ジッタ**: 再試行のたびに待ち時間を倍にし(指数)、
  ランダムなばらつき(ジッタ)を混ぜることで、複数クライアントが一斉に
  再試行して相手サーバをさらに苦しめる事故を防ぐ。
- **タイムアウト**: C#の`CancellationTokenSource.CancelAfter`に相当する
  `AbortSignal.timeout(ms)`を使う。

## 課題

| 課題 | 内容 | 目安 |
|------|------|------|
| ex01_parse_response | 外部APIの生JSON(DTO)をドメインモデル(Book)へ変換 | 10分 |
| ex02_zod_schema | zodスキーマの定義とsafeParseによる実行時検証 | 15分 |
| ex03_retry_timeout | リトライ可否判定・指数バックオフ・AbortSignalタイムアウト | 15分 |
| ex04_capstone | fetch注入+リトライ+zod検証+DTO変換を1つの関数にまとめる | 15分 |

外部APIへの実際の通信は行わない。すべてのモジュールはfetch互換の関数を
引数で受け取る設計(依存性注入)にし、テストではダミーの`Response`を返す
fake fetchを渡す。

## マイルストーン(全部チェックできたらユニット完了)

- [ ] 「TSの型は実行時に消える」ことを説明でき、外部から来たJSONをzodの
      safeParseで検証してから使える
- [ ] 外部APIのレスポンス形(DTO)とアプリ内のドメインモデルを分け、
      変換関数を書ける
- [ ] HTTPステータスから「リトライすべき失敗」と「即座に諦めるべき失敗」を
      切り分けられる
- [ ] 指数バックオフ+ジッタのリトライとAbortSignalによるタイムアウトを
      async関数として実装できる
- [ ] fetchを注入可能にして、ネットワークなしでAPIクライアントを
      テストできる
