# ex04_capstone ヒント

## fetchBooksRobustly

### tier1
これまで作った3つの部品を順番につなげるだけの関数。①通信+リトライ ②検証
③ドメインモデルへの変換。新しいロジックは書かない。それぞれの部品が
何を受け取り何を返すかを思い出せば、つなぎ方は1本道になる。

### tier2
①`await fetchWithRetry<unknown>(fetchFn, url, options)`で生JSON(まだ型は
unknown)を取る。②`parseBookDtoList(raw)`に渡す。結果の`ok`が`false`なら、
`ResponseValidationError`(すでにex02からimport済み)を`error`の内容を
含めてthrowする。`ok`が`true`なら`result.data`を③`toBooks(...)`に渡して
returnする。

### tier3
```ts
const raw = await fetchWithRetry<unknown>(fetchFn, url, options);
const parsed = parseBookDtoList(raw);
if (!parsed.ok) {
  throw new ResponseValidationError(`... ${parsed.error}`);
}
return toBooks(parsed.data);
```

## fetchBooksSafely

### tier1
「エラーを2種類に区別する」というこのユニットのテーマの総仕上げ。
`fetchBooksRobustly`をtry/catchで包み、catchできたエラーの「種類」を
`instanceof`で見分ける。C#の`catch (SpecificException ex)`のように
型で分岐するのと同じ発想(TSでは`catch`自体は型を絞れないので、
catchした後に`instanceof`で自分で判定する)。

### tier2
```
try {
  const books = await fetchBooksRobustly(fetchFn, url, options);
  return { ok: true, books };
} catch (error) {
  ...
}
```
catchの中で`error instanceof ResponseValidationError`が真なら
`reason: "validation"`、そうでなければ`reason: "network"`。
メッセージは`error instanceof Error ? error.message : String(error)`で
安全に取り出す。

### tier3
```ts
try {
  const books = await fetchBooksRobustly(fetchFn, url, options);
  return { ok: true, books };
} catch (error) {
  const message = error instanceof Error ? error.message : String(error);
  const reason = error instanceof ResponseValidationError ? "validation" : "network";
  return { ok: false, reason, message };
}
```
