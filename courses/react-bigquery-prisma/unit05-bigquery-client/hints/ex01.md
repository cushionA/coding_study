# ex01_build_schema ヒント

## mapFieldType

### tier1
5種類しかない対応関係を、switchやif文の連打ではなく「表(マップ)」として
持たせると読みやすい。C#で言えば`enum`から別の値へ変換するときに
`Dictionary<T, U>`を1個持つのと同じ発想。

### tier2
`Record<FieldType, BigQueryFieldType>`という型の定数オブジェクトを
関数の外(またはローカル)に用意し、`type`をキーにして引くだけで済む。
switch文で書いても構わない。

### tier3
```ts
const MAP: Record<FieldType, BigQueryFieldType> = {
  string: "STRING",
  int: "INT64",
  float: "FLOAT64",
  boolean: "BOOL",
  timestamp: "TIMESTAMP",
};
return MAP[type];
```

## buildSchemaField

### tier1
この関数は新しい判断を1つだけ追加する: 「nullableかどうか」から
modeを決める。型の変換自体はすでにmapFieldTypeが知っている。

### tier2
`mapFieldType(spec.type)`でtypeを求め、`spec.nullable`が truthy かどうかで
`"NULLABLE"`か`"REQUIRED"`を選ぶ三項演算子1本で書ける。

### tier3
```ts
return {
  name: spec.name,
  type: mapFieldType(spec.type),
  mode: spec.nullable ? "NULLABLE" : "REQUIRED",
};
```

## buildTableSchema

### tier1
「配列の各要素に同じ変換を適用する」ときにforループを書く必要はない。
C#の`list.Select(x => ...)`にあたる配列メソッドがある。

### tier2
`specs.map(buildSchemaField)`のように、関数そのものを渡せば1行で済む
(`specs.map(spec => buildSchemaField(spec))`と書いても同じ)。

### tier3
```ts
return specs.map(buildSchemaField);
```

## buildAuthorSummarySchema

### tier1
「著者別に何冊あるか」を集計するには何の列が要るかを先に考える:
①誰の(author) ②何件か(bookCount) ③いつの情報か(lastIngestedAt)。
そのうえで、すでに書いたbuildTableSchemaにFieldSpecの配列を渡すだけ。

### tier2
`author`はSTRING(必須)、`bookCount`はINT64(必須)、`lastIngestedAt`は
TIMESTAMPだがまだ集計対象になったことがない著者もいるのでnullable。

### tier3
```ts
return buildTableSchema([
  { name: "author", type: "string" },
  { name: "bookCount", type: "int" },
  { name: "lastIngestedAt", type: "timestamp", nullable: true },
]);
```
