# unit12: 軽量モデルの段階表 — CPUだけで安く済ませる

このユニットを終えると、「このタスクにどの道具を使うか」を**精度とコストの両方の数字で**答えられるようになる。
一番軽い道具から始めて、必要になったときだけ上の段に上がる、という判断の型を身につける。

## なぜ学ぶか: 本番サーバーは CPU しかない

本番の推論サーバーは CPU のみ(GCP の T2D 相当)。生成 LLM はそもそも載らない。
だが実務でやりたいことの大半 —— 商品カテゴリの分類、名寄せ、ブランドや型番の抽出 —— は
**もっと軽い道具で足りる**。問題は「どれで足りるか」を、勘ではなく数字で判断できるかだ。

日次で数万〜数十万件を捌くとき、1件あたり 0.1 ミリ秒と 10 ミリ秒の差は
そのままインスタンス台数の差になる。逆に、精度が 3 ポイント足りないせいで
人手の確認が毎日発生するなら、重い段に上がる方が安い。**この天秤を数字で組めるようにする。**

## 段階表

| 段 | 道具 | 何をするか | 負荷 |
|---|---|---|---|
| 0 | 辞書・正規表現 | 決まった書式の抽出、列挙できる集合の照合 | 極軽 |
| 1 | 形態素解析 | 分かち書き。全ての前段 | 極軽(だが**実は律速**) |
| 2 | 軽量教師あり分類 | 大量テキストの分類 | 極軽 |
| 3 | 文埋め込み(bi-encoder) | 類似検索・名寄せの一次絞り | 軽 |
| 4 | クロスエンコーダ | ペアの精密判定 | 中 |
| 5 | 系列ラベリング(NER) | 固有表現の抽出 | 中 |
| 6 | 小型生成モデル(seq2seq) | 柔軟な変換 | 中〜重 |
| — | 生成 LLM | — | **載せられない**。理由を数字で示す |

## 概念の顔見せ: 「上の段ほど良い」ではない

このユニットで一番大事なのは、**対象の性質で答えが変わる**という事実だ。実測すると:

- **型番の抽出** — 書式が増え続けるので、**学習モデルが勝つ**(0.9478 vs 規則 0.4422)
- **ブランドの抽出** — 列挙できる集合なので、**辞書が勝つ**(0.9778 vs 学習モデル 0.8847)。しかも 185 倍速い
- **完全に新しい書式** — **どちらも 0 点**。例が無ければ学習モデルも学べない

C# で言えば、`Dictionary` の完全一致で済むものにわざわざ推論を挟まない、というだけの話。
だが「機械学習を使うべきか」の判断は、実務では驚くほど雑に行われる。

## 環境についての注意

**速度の数値は実行するマシンで変わる。** そのためチェックポイントは精度・件数・ロジックだけを見る。
速度は lesson の中でその場で測り、本番インスタンスの時間単価に換算する —— という手順そのものを学ぶ。
実務でも「自分の環境で測ってから本番に換算する」が正しい順序で、他人の測定値を鵜呑みにしてはいけない。

> **`fastText` について** — 段2 の本命は本来 fastText だが、`fastText 0.9.3` は
> numpy 2.x で `predict()` が動かない(削除済みの `np.array(copy=False)` を使っているため)。
> この教材では同じアーキテクチャ(ハッシュ化した単語 n-gram + 線形分類器)を
> scikit-learn で実装する。**本番採用時は numpy を 1.x に固定するか、C++ 実装を直接叩く必要がある。**

> **事前学習済みモデルについて** — 文埋め込みの本命は e5 などの学習済みモデルだが、
> この教材の検証環境からは取得できなかったため、疑似埋め込みで代替している。
> **仕組みと評価の方法は本物で学べる**が、絶対的な精度は実モデルとは異なる。
